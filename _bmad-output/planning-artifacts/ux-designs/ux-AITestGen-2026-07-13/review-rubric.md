# Spine Pair Review — AITestGen

## Overall verdict
The spine pair is a largely strong, source-extractable contract: token typing is thorough, section order matches the canonical shape, mockups/sources all resolve, and the extensive prototype-reconciliation discipline (adopted/rejected/GAP tags) is a genuine strength rare in this kind of document. It's undercut by one critical defect — EXPERIENCE.md's Key Flow 3 treats PRD UJ-2 as a still-open, blocked item, when the current PRD explicitly states UJ-2 was **removed in full** — plus a cluster of real component/state gaps (badge, kebab-menu, icon-button, and the top bar's click behavior have no dedicated coverage; Connect App's reachability-validation FR has no represented state anywhere).

## 1. Flow coverage — adequate
Checked: PRD §2.3 Key User Journeys against EXPERIENCE.md Key Flows. The current PRD (`prd.md`, updated 2026-07-21) contains exactly one live UJ — **UJ-1** (§2.3 line 43) — since UJ-2 was removed in full on 2026-07-15 (§2.3 line 51, §6.2 line 265, §9 line 308). UJ-1 has a full, well-formed Key Flow (EXPERIENCE.md Flow 1, lines 134-145): named protagonist (Maria), 8 numbered steps, an explicit **Climax:** and **Resolution:**, matching the shape's requirements.
### Findings
- **critical** EXPERIENCE.md's Flow 3 ("Devon checks release readiness," lines 153-160) is framed as `[BLOCKED, carried forward unchanged]` and states "This still needs explicit product-level resolution via the PRD" — but the sourced PRD already resolved this: UJ-2 was **removed in full** (PRD §6.2 line 265: "UJ-2 (Devon's release-readiness journey, §2.3) — depended entirely on the removed executive dashboard"; §9 line 308 confirms "UJ-2 removed"). A downstream consumer would chase a requirement the PRD no longer contains. *Fix:* either delete Flow 3 (its struck-through content already reads as archival) or rewrite its framing to state the PRD closed this by cutting UJ-2, and that reviving it needs a fresh product decision — not present it as a standing open item awaiting resolution.
- **high** FR-31 (Application reachability validation, PRD lines 94-102, added 2026-07-21, not deferred/cut) has zero representation anywhere in EXPERIENCE.md — no flow step, no Component Patterns rule, no State Patterns row for a failed reachability check on Connect App. (location: EXPERIENCE.md Component Patterns "Connect App form" row, line 89; State Patterns table, lines 96-103). *Fix:* add an explicit error/blocked-submit state for a failed reachability check.
- **low** Flow 2 (Landing persistence illustration, lines 147-151) has no explicit **Climax:** label and no failure path, unlike Flow 1's format — likely fine given its narrow illustrative purpose, but worth aligning formatting if it's meant to read as a peer flow.

## 2. Token completeness — adequate
Checked: every frontmatter token in DESIGN.md's `colors`/`typography`/`rounded`/`spacing`/`components` blocks against every `{path.to.token}` reference in the prose, per design-md-spec's type rules.
### Findings
- **medium** `colors.surface-sunken` (line 15, `#F8FAFC`) and `colors.good-wash-strong` (line 31, `#DCFCE7`) are defined in frontmatter but never referenced or explained anywhere in the body (Colors, Components, or Do's/Don'ts). `surface-sunken` is also an exact hex duplicate of `canvas-wash` with no stated distinction of when to use one vs. the other. *Fix:* delete the unused tokens, or add the missing usage note.
- **medium** `colors.accent-wash-soft`, `colors.accent-wash`, `colors.accent-wash-strong` (lines 25-27) are `rgba(...)` strings, not hex strings — design-md-spec.md (line 15) requires colors to be hex strings (`'#FBF9F4'`). The prose rationale (computed opacity washes off the accent) is reasonable, but the literal token format deviates from spec. *Fix:* either note this explicitly as an intentional spec extension, or express as 8-digit hex.
- **medium** No contrast ratio is stated for load-bearing color-on-tint combinations beyond the `ink-muted`/`ink-faint` pair (which does get ratios, ~4.6:1 and ~2.9:1, DESIGN.md Colors section) — e.g. the badge/status-pill wash+text pairs (`happy-wash`/`accent-strong`, `danger-wash`/`danger-strong`, `warn-wash`/`warn-strong`, `good-wash`/`good-strong`) and `button-primary`'s white-on-accent fill have no stated AA ratio, despite Accessibility Floor claiming "WCAG 2.1/2.2 AA is the floor" (EXPERIENCE.md line 117). *Fix:* state ratios for these combos, or note they're inherited/pre-verified from the prototype.

## 3. Component coverage — thin
Checked: every component name used anywhere (frontmatter `components` block, DESIGN.md Components section, EXPERIENCE.md Component Patterns table) for a matching row in both.
### Findings
- **high** Three frontmatter component tokens — `icon-button` (line 144), `kebab-menu` (line 180), `badge` (lines 188-196, with 3 named variants) — have full visual token definitions but **no dedicated bullet in DESIGN.md's Components section** and **no row in EXPERIENCE.md's Component Patterns table**. They surface only as passing plain-text mentions inside other components' prose (Colors section line 274, Shapes section line 301, Do's/Don'ts line 339) — never via `{components.badge}`/`{components.kebab-menu}`/`{components.icon-button}` token markup, and never with their own anatomy/behavior writeup. *Fix:* add a Components-section bullet and an EXPERIENCE.md Component Patterns row for each, especially `badge` and `kebab-menu` which are used on every list screen.
- **high** Top bar's interactive behavior — brand-mark/wordmark click returns to Landing; user-avatar click opens a menu (name, email, Log out) — is specified only in DESIGN.md's "Top bar" bullet (line 314, a visual doc) with **zero corresponding row in EXPERIENCE.md's Component Patterns table**. This is a global, every-screen nav element with no behavioral spec in the behavior-owning document. *Fix:* add a "Top bar" row to EXPERIENCE.md Component Patterns.
- **medium** "Discovery Progress" has a dedicated DESIGN.md Components bullet (line 323, including a behavioral aside about rejecting the rotating caption) but no matching named row in EXPERIENCE.md's Component Patterns table — its behavior is folded into the State Patterns table instead (line 98, "Discovery running / completing"), a table meant for surface states, not component interaction rules. *Fix:* either add a Component Patterns row, or rename to make clear State Patterns is the canonical home for this one.

## 4. State coverage — adequate
Checked: every IA surface (Sign In, Landing, Connect App, Discover Journeys, Review Scenarios, Generate Suite, Suite Generated) against expected states (empty, cold-load, error, cleared, onboarding).
### Findings
- **high** Connect App (pipeline step 1) has no defined state for a failed reachability check (FR-31, PRD lines 94-102) — no inline error, no blocked-submit treatment, nothing. This is a confirmed, non-deferred FR with direct UX implications. (Same underlying gap as Flow coverage finding above — flagged here because it's specifically a missing *state*, not just a missing flow step.)
- **low** No loading/transition state is defined between clicking "Generate Test Suite" and the Suite Generated screen appearing — likely near-instant given FR-16 generates immediately on discovery, but the doc doesn't say so either way.
- **low** No input-validation state exists anywhere in State Patterns for Connect App's other required fields (Application name, Base URL format, credential fields) — probably standard/out-of-scope for the spine, but worth a one-line note if intentionally deferred to implementation.

## 5. Visual reference coverage — strong
Files in `mockups/`: `prototype-v1.html`, `prototype-v2-standalone.html`, `prototype-v3.html` — all three are named and disposed of inline (current vs. historical) in EXPERIENCE.md's opening blockquote (line 13) and DESIGN.md's frontmatter description (line 3). `imports/` is empty — nothing to reference, no orphans.
### Findings
- **low** The composition-reference line (EXPERIENCE.md line 13) never states a general "spine wins over mockup on conflict" rule the way both shape examples do verbatim next to their own composition reference (`design-example-shadcn.md`'s and `-mobile.md`'s EXPERIENCE files both append "Spine wins on conflict."). AITestGen's line only states that DESIGN.md wins over EXPERIENCE.md for visual properties — never that the spine as a whole outranks `prototype-v3.html`. Given how much of this document *is* a mockup reconciliation, the rule is demonstrated case-by-case throughout but never stated once as a standing principle. *Fix:* append "Spine wins on conflict" (or equivalent) to the composition-reference line.

## 6. Bloat & overspecification — adequate
No persona/FR restatement, prose-vs-table balance is reasonable, and DESIGN.md's literal pixel values are base token definitions rather than redundant restatement.
### Findings
- **low** The "changed from the 2026-07-15 revision" historical narrative (teal→blue, flat→shadow-elevation, no-gradient→two-gradients) is repeated across at least four sections (Brand & Style line 260, Colors line 272/275, Elevation & Depth line 293, echoed again in Shapes/Typography asides) — reads as changelog commentary re-litigated four times rather than stated once. Not fatal, but a trim candidate for a downstream reader who only needs current state.

## 7. Inheritance discipline — thin
Sources frontmatter resolves cleanly (all 3 paths in both files' `sources:` list exist on disk). Glossary terms match the PRD's own shorthand convention (Capability/Journey). EXPERIENCE.md's cross-doc token references (`{DESIGN.md#Colors}`, `{DESIGN.md#Components}`, `{DESIGN.md#colors.ink-muted}`) all resolve to real DESIGN.md content by name.
### Findings
- **critical** (repeated from Flow coverage, primary home here): EXPERIENCE.md cites "PRD UJ-2" as a real, currently-tracked source identifier needing future resolution, but the current PRD's own text disposes of it as **removed in full**, not "blocked." This is a verbatim-naming/source-fidelity break, not just a missing flow — the spine is citing a source item that no longer exists in the source. This is the one finding that most needs a fix before this pair is treated as a clean contract.

## 8. Shape fit — strong
DESIGN.md section order: Brand & Style → Colors → Typography → Layout & Spacing → Elevation & Depth → Shapes → Components → Do's and Don'ts — exact canonical order, nothing out of place. EXPERIENCE.md has all 8 required defaults (Foundation, IA, Voice and Tone, Component Patterns, State Patterns, Interaction Primitives, Accessibility Floor, Key Flows) plus two well-placed optional sections (Review & Trust Model, Inspiration & Anti-patterns). Responsive & Platform is justifiably omitted — Foundation states "Desktop web app only — no mobile or tablet form factor," the same single-surface justification `experience-example-mobile.md` uses for the same omission.
