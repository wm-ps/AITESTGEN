How Explorer works

Explorer learns a web application by using it in a real browser, the way a careful tester would. It ends up with test scenarios that it has already proven work. This page goes through every stage in plain words. The small grey references point to the code, so you can check any detail.

The big picture

One run goes through nine stages. One Temporal workflow (ExplorerRunWorkflow) runs all of them in order. Click a stage to jump to it.

1 · First lookVisit every screen it can and describe each one 2 · Your reviewYou confirm the summary, set a goal and skip screens 3 · MissionsCarry out real tasks end to end 4 · HuntFind screens that only appear sometimes 5 · BreadthUnlinked pages, roles 6 · PlanWrite the scenarios 7 · ProveRun, break on purpose, replay 8 · JourneysGroup the proven scenarios 9 · Test casesGenerate tests and run them
The one-line versionExplorer learns the app (1), you tell it what matters (2), it does the real tasks (3), looks for hidden screens (4–5), writes scenarios from everything it learned (6), proves each one really works (7), and hands the proven ones to Vantage as Journeys, Scenarios and test cases (8–9).

Words you'll see

New users mix these up most often. They are different things.

Mission

A task Explorer sets itself so it can learn the app, such as "Create a new claim". It is never a test and never shows up in Journeys.

Scenario

One test: one action and one visible result, for example "Policy number is required". It is written in plain English first; its code comes later.

Just a folder, created at the very end, that groups proven scenarios. It is named after a screen or after a whole task.

1First look: learning the app

Visit as many screens as possible, describe each one, and save it all. There is no goal yet, so it explores everything.

What it does

  1. Signs in. If the app has no login, it just opens it. For SSO it loads the saved cookies. For a username and password it finds the password box, fills it and the field before it, and submits.
  2. Starts from the last map if this app was explored before, and then needs fewer new screens.
  3. Opens menu groups to reveal hidden menu items. This is plain code, without the model.
  4. Keeps a "to visit" list built from the model's suggestions and the page's links. The fast model picks the next one.
  5. Goes there:
    • For a link, it clicks it and reads the new screen.
    • For a task (such as "New Claim"), it walks through the form step by step, filling fields and pressing Next, and notes every choice point. It stops before the final Submit.
  6. Repeats until it has 150 new screens, 120 minutes have passed, or nothing is left to visit.
  7. Writes the App Summary from the saved screens, then waits for you.

Where the data on each screen comes from

① A DOM scan

One JavaScript snippet reads the visible elements: title, headings, links (150), menu items (80), buttons (60), fields with label, type, required flag, options and min/max/pattern (60), tables (headers and row count), alerts, and the first 2,500 characters of text.

browser.py:190 _INVENTORY_JS

② A screenshot

A JPEG of the page. The model looks at it, so it sees what a person sees.

browser.py:538 Eyes.look

③ Browser listeners

These run all the time and catch console errors, crashes, 4xx/5xx responses, loads slower than 6 seconds, and every API call the page makes.

The screenshot and a trimmed copy of the scan go to the model (brain.perceive). It answers with a reading of the screen:

  • its name, the record it is about (such as Claim), its kind (list, form, detail…), mode and purpose;
  • its fields and actions, with risky ones flagged;
  • hints that something is hidden, and problems it noticed;
  • places worth visiting next, and records the app created.

A screen already read in this run is not sent to the model again.

3Missions: doing the real tasks

The first look covers the app broadly. Missions go deep on the tasks inside your goal and finish them.

Planning

The model reads the scope, your answers, the choice points and the screens inside your goal. It writes 8–15 missions, each with a kind (taskbrancharearule), a priority, a start screen, instructions and an expected result.

Running

Up to 3 missions run at once (only 1 if the app seems to keep state per account). Each one walks its task step by step:

  1. The model looks at the screenshot and decides what to fill, choose and press.
  2. Code finds the element and does it. The exact way it found the element is recorded.
  3. Safety gate: Delete, Pay, Transfer, Approve, Log out and Cancel always need your OK. A final Submit or Save is pressed automatically only on a non-production app; otherwise it asks "May I press X?".
  4. If it goes in circles or gets stuck, it asks you once, then stops.
  5. At the end, the model compares what happened with what was expected. A mismatch becomes a finding plus an "Is this a bug?" question, which never blocks the run.
  6. Options it didn't try become follow-up missions.

How questions work

Explorer first reuses an earlier similar answer if there is one. Otherwise it emails you and checks every 5 seconds for up to 10 minutes. If nobody answers, it carries on. Your answer is saved as knowledge, so all later steps use it even if it arrives late.

4Hunt: screens that only appear sometimes

This runs only after all missions are done. It is plain code with no model, it stays on one screen at a time, and it never presses Next or Submit.

Every option

On up to 10 forms, it picks each option of every dropdown and radio group (up to 4 groups × 5 options) and records any fields that appear. Example: "Married" shows the spouse fields.

Amounts

It types 1, 999, 15,000 and 1,000,000 into amount fields and records any new sections. Example: an approval panel above 15,000.

Fake server answers

Inside its own browser only, it pretends the server returned no data, an error, every feature switched on, or a date a year from now. The real server is never changed.

MissionsHunt
Question it answersWhat happens if I go down this path?What appears on this screen when this changes?

Each find is saved as a screen with a condition, such as "only appears when Marital status is Married". Variants found from options and amounts are used when planning scenarios. Variants from fake server answers are not, because a real test can't reach them. A screen that goes blank on a server error is logged as a finding.

Scenarios come from three sources. They all go into one list, and the total is what you see.

Confirmed App Summary and scope—

Screens are sent three at a time, with up to 4 calls running together. For each screen, the model works through the checklist and writes one scenario per item that applies:

List screens · L-01…L-23

Page loads, columns, data matches the server, count, empty state, search, filters, sort, paging, open, edit, delete (then cancel or confirm), add, export.

Form screens · F-01…F-20

Loads, defaults, dropdown options, edit pre-fill, required fields, format, length, range, conditional fields, create, saved correctly, appears in list, update, cancel, reset, double submit.

Other · P-01 and X-

Other pages: loads, its links lead to the right screen, Back and Refresh keep the user in place. X- items: your answers and confirmed rules, hidden choices, possible bugs.

Rules it follows: one action and one result per test; only fields and buttons that the screen really has; anything you confirmed gets a test first, marked confirmed; no final Save on production; never pay, delete or cancel unless you approved that button.

A second model call (review_plan) then drops only exact duplicates and scenarios that need a screen or step Explorer never saw. Finally the list is capped at Max scenarios (150) and spread evenly across screens.

A: which missions become whole-flow scenarios

A mission qualifies only if all four are true:

  1. It finished. Stuck or blocked missions are out.
  2. It is not a rule check.
  3. It took 5 or more steps.
  4. It is an original mission, or a follow-up that found new screens.

The qualifying missions are sorted by new screens found, then by steps, and the top 8 are kept.

Each kept mission becomes one scenario. Its title is the mission's title. It starts on the home screen, its instructions are the mission's goal plus "do the whole task from start to finish", and its expected result is the mission's expected result. It gets up to 40 steps. The mission's clicks are not copied; the flow is walked again in stage 7.

Missions that qualify but don't make the top 8Their exploring is not wasted. Their screens, links, outcomes, your answers and any bugs all still feed the checklist scenarios. What they lose is an end-to-end test of the whole task and a Journey folder of their own. The 8 is a fixed number in the code (MAX_JOURNEYS, tests_stage.py:84) with no documented reason; most likely it limits cost, since whole-flow scenarios are the most expensive kind. The ranking uses new screens found, not business importance.

7Build & prove

The model is used only once, in the first run. Every later run replays the exact recorded steps in code.

RunWho drivesWhat happensFails if
1 · BuildModelStarts on the home page and reaches the start screen, by the saved route if there is one. Carries out the plain-English scenario step by step, recording each action and its locator. Then the model chooses a proof: text visible, URL contains, or an API call. A proof that was already on screen before the test acted is rejected.It can't finish, even after one retry with a note on what went wrong, or no reliable proof is found
2 · Broken on purposeCodeReplays the steps without the last real action, usually the final click. If the proof still appears, it tries again without the last value typed or chosen. Steps that only reach the screen are never removed.The proof still appears, which means the test wouldn't catch a real problem
3 · Proof replaysCodeReplays all the steps "Proof replays" times (default 1), recording a video.Any replay gives a different result

The result is proven if the model said it matched what was expected, and known_bug if it didn't. Otherwise it is dropped. The Playwright code is made from a template using the recorded steps and the proof; the AI doesn't write it.

•How elements are found (locators)

No ids or CSS classes are needed. Explorer finds elements the way a person does, which is also what Playwright recommends.

LocatorFindsMatches, for example
getByRole('button', {name: 'Submit'})a button named "Submit"<button class="css-1x9k2">Submit</button>
getByLabel('Policy number')the field linked to that label<label for="p1">…<input id="p1">
getByPlaceholder(…)an input with that placeholder
getByText(…)an element showing that text
  1. Build run: the model names an element by its visible text, such as "Submit" or "Policy number".
  2. Code tries a fixed list of ways to find it: role, then exact text, then placeholder, then label, then the field after a caption, and so on. The first one that matches is used and saved on the step.
  3. Replays and the exported test use only that saved locator. There is no guessing and no model.
  4. The route to a scenario's start screen reuses locators recorded by earlier walks (ExplorerScreen.route).
{do: "click", label: "Submit", locator: {by: "role", role: "button", name: "Submit", exact: true}}
→ page.getByRole("button", { name: "Submit", exact: true }).filter({ visible: true }).first()
Elements with the same nameHidden duplicates are ignored, but among visible ones Explorer always takes the first. "Edit" on every row of a table means row 1 gets clicked. Explorer has nothing yet that scopes to a container, such as "the Edit in the row for POL-123".

9Test cases & running them

  1. Generate tests (on Explorer's Scenarios tab) starts suite generation for each Journey.
  2. For each scenario, if the proven code typechecks it is used as-is. Only if it doesn't is the code written by the AI. One scenario = one test case.
  3. Running the tests: each test runs, gets healed if it fails, and is reported. Apps that keep state per account run their tests one at a time.

Known gaps

Only 8 whole-flow tests

The cap is fixed and ranks by new screens found, so an important but short flow can be cut.

Same-name elements

The first visible match always wins. There is no scoping to a row or section.

Planning sees little of each mission

Only its title, outcome and whether it went as it should. Its steps and the values it entered are not passed on.

Hunt opens screens by address

Wizard steps you can only reach by clicking through earlier steps may not be checked.

Late answers

An answer that arrives after the 10-minute wait only helps later steps.

No schema check on model replies

A badly formed reply is patched with defaults instead of being rejected.
